# Offline retrieval measurements (2026-11-01)

All numbers come from production candidates read over read-only psql and reranked directly against
the production reranker (`Dongjin-kr/ko-reranker`, `http://192.168.150.37:8891/v1/rerank`). The same
30 golden queries, the same 512-dim query embeddings (`kakaocorp/kanana-2-3b-embedding`), and memo-level
recall over the top 10 are used everywhere.

`backend/eval/offline-2026-11-01.json` has the per-query breakdown.

## Why this is not the live baseline

The live baseline (`baseline-2026-11-01.json`) is the current deployed `/api/v1/search` pipeline,
which already reranks with its own query and document construction. These offline runs rebuild only
the candidate pool and apply one variant at a time, so **compare variants with each other, not with
the live numbers**.

## Keyword arm: pg_trgm vs `to_tsvector('simple')` vs none

| pipeline | recall@10 | MRR@10 | distinct memos |
| --- | --- | --- | --- |
| vector only | 0.5076 | 0.4591 | 6.59 |
| RRF vector + pg_trgm (0.5/0.5) | 0.5076 | 0.4602 | 7.32 |
| RRF vector + `simple` FTS (0.5/0.5) | 0.4848 | 0.4182 | 6.45 |

The `simple` FTS arm with title weighting loses to plain pg_trgm and to vector-only, so it was **not**
adopted. pg_trgm adds no recall either, and for Korean-only queries it returns rows with no shared
trigrams. Per the approved fallback, the keyword weight is now 0 for CJK queries with no Latin or
digit token, and that arm is skipped entirely (one less DB query per search). Mixed queries such as
`sparrow.properties 메트릭 설정` keep the balanced 0.5/0.5 profile because their Latin tokens do
produce trigrams.

## Rerank document construction

Candidates: vector top 40 per query, reranked as one batch, per-memo cap of 3, top 10 kept.

| rerank document | recall@10 | MRR@10 | distinct memos |
| --- | --- | --- | --- |
| chunk content only | 0.4318 | 0.3709 | 8.05 |
| `Title` + `Full content summary` + `Chunk content` | 0.4924 | 0.3525 | 7.32 |

The shared construction recovers **+0.061 recall@10** at an unchanged candidate pool (the measured
single-document gap was 0.0002 vs 0.903). MRR drops slightly because a broader document can outrank a
narrower exact chunk; the live path also reranks against the rewritten query, which raises
precision.

## Rerank query: rewritten query alone vs wrapper

For the five golden queries where the mechanical expansion changes the query:

| query | expected memo score, expanded alone | expected memo score, wrapped |
| --- | --- | --- |
| checker-rule-file | 0.831 (rank 2) | 0.418 (rank 5) |
| title-metric-display | 0.997 (rank 1) | 0.293 (rank 1) |
| sparrow-properties-metric | 0.722 top-1 | 0.651 top-1 |
| sast-dast-difference (negative) | 0.918 top-1 | 0.953 top-1 |
| enterprise-backend-error-codes | 0.999 top-1 | 0.998 top-1 |

Sending the wrapper (`original\n\nRewritten retrieval query: ...`) dilutes the rerank query: the
expected memo drops by up to 0.70 relevance. `buildRerankQuery` now sends the rewritten query alone.

## Dedupe and per-memo cap

Before this change the same chunk text could appear four times in ten results. Deduplicating by
`(memo_uuid, trimmed chunk_content)` and capping a memo at 3 chunks raises mean distinct memos from
6.59 (vector arm) to 8.05 after rerank without dropping any expected memo, and the cap is applied
both before reranking (so diverse memos reach the reranker) and when building the final window.

## Query rewrite for `/api/v1/search`

`SEARCH_QUERY_REWRITE_ENABLED` (default `true`) rewrites the query with the existing
`LLMService`-backed `rewrite()` path and searches both the original and rewritten queries as vector
arms, merging by best distance. Explicit identifier queries skip the rewrite so Jira keys and doc
refs stay verbatim. The reranker then receives the rewritten query alone. Set
`SEARCH_QUERY_REWRITE_ENABLED=false` to restore single-query search without a code change.

## No new index

No `to_tsvector('simple')` arm was adopted, so **no new database index is required**. The existing
pg_trgm index continues to serve mixed-script queries.
